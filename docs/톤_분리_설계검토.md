# 사주 소견 톤 분리 설계 검토서

> 목적: "할머니 말투 풀이"와 "전문용어 설명"을 체계적으로 구분한다.
> 원칙: 대규모 재작성 금지 → 기존 구조를 최대한 활용해 최소 시행착오로 진행한다.

---

## 1. 현황 진단 (코드 조사 결과)

### 1-1. 이미 존재하는 분리 골격
결과 화면은 이미 4개 탭으로 나뉘어 있다 (`render_single_page_buttons`):

| 탭 | 함수 | 현재 성격 |
|----|------|-----------|
| 🏥 진단서 | `render_hanuneyo_text_explanation` | **할머니체 + 전문내용 혼재** |
| 📡 사주예보 | `render_sewun_text_overview` | 할머니체 위주 |
| 🪪 원국 | `render_origin_identity_table` | 표 위주(중립체) |
| 🔎 상세 | `render_detail_tabs` | **전문체 위주** |

→ **큰 그릇은 이미 있다.** "진단서=쉬운말 / 상세=전문가"라는 의도가 코드 주석에도 명시돼 있음
(`render_single_summary` docstring: "일반인용 한눈에 보기와 전문가 상세보기로 분리").

### 1-2. 문제의 핵심
분리 의도는 있으나 **경계가 새고 있다**:

1. **진단서 탭 안에 전문 파트가 섞임** — `render_hanuneyo` 내부에 `#### 📋 처방전`,
   `흐름과 연결(식상생재·재생관·관인상생)` 같은 전문 expander가 들어가 있음.
2. **말투 텍스트가 코드 전역에 하드코딩** — "거든" 100곳, "~봐." 81곳, "해봐" 30곳.
   톤 문자열이 함수마다 흩어져 있어 한 곳에서 못 바꿈.
3. **용어 시스템은 있으나 연결이 약함** — `GLOSSARY`(37개 용어),
   `render_glossary_popovers`, `quest_title(terms=...)` 인프라가 이미 있지만
   할머니체 문장과 전문용어가 한 문장에 섞여 나옴.

### 1-3. 자산 (재활용 가능)
- `GLOSSARY` 딕셔너리 37개 용어 정의 — **그대로 전문 설명의 씨앗으로 사용 가능**
- `render_glossary_popovers` / `render_glossary_tab` — 용어 팝오버 렌더러 존재
- 탭 4개 구조 — 그릇 존재
- 신살 카드의 이중 구조 선례: `_SH_DOC_TEXT`(할머니체) + `_shinsal_card_profile`(전문 how/meaning)
  → **이미 한 곳에서 두 톤을 분리해 쓰는 패턴이 존재한다. 이걸 표준으로 확장하면 됨.**

## 2. 설계 방안 — 3가지 안 비교

### 안 A. "한 문장 두 줄" 방식 (인라인 병기)
각 소견 문장 아래에 회색 작은 글씨로 전문 설명을 붙인다.
- 장점: 탭 이동 없이 바로 보임. 구현 단순.
- 단점: 화면이 길어지고 잡다해짐. 할머니체의 "편안함"이 깨짐. 모바일에서 답답.

### 안 B. 탭 경계 정리 (권장) ★
"진단서=순수 할머니체 / 상세=순수 전문체"로 **경계만 깨끗이 가른다.**
진단서에서 전문 expander(처방전·식상생재 등)를 빼서 상세 탭으로 이동.
- 장점: 기존 구조 그대로. 함수 이동만 하면 됨. 시행착오 최소.
- 단점: 전문 내용을 보려면 탭을 옮겨야 함(단, 이게 정상적 UX).

### 안 C. 용어 토글 방식
화면 상단에 "쉬운말 ↔ 전문가" 토글 하나. 같은 내용을 두 버전으로 작성해 전환.
- 장점: 가장 깔끔한 UX.
- 단점: **모든 소견 문장을 2벌씩 작성**해야 함 → 대규모 재작성. 원칙에 위배.

### 권장: **안 B를 뼈대로, 안 A의 "용어 칩"을 부분 적용**
1. 탭 경계를 깨끗이 정리(안 B)하여 큰 틀을 먼저 세운다.
2. 할머니체 문장에 나오는 전문용어만 `GLOSSARY` 팝오버 칩으로 처리(안 A 축소판)
   → 문장은 할머니체 유지, 용어는 탭 누르면 정의가 뜨는 방식.

## 3. 톤 표준 정의 (작성 가이드)

| 구분 | 할머니체 (진단서·예보) | 전문체 (상세) |
|------|----------------------|---------------|
| 호칭 | "~야", "~거든", "~해봐" | "~입니다", "~로 봅니다" |
| 용어 | 한자·전문어 최소화, 쓰면 칩 처리 | 정식 명리 용어 사용(식상생재 등) |
| 목적 | 위로·방향 제시 | 근거·계산 논리 |
| 길이 | 짧고 따뜻하게 | 정확하고 구조적으로 |

이 표를 코드 상단 주석으로 박아두면 향후 문장 추가 시 흔들리지 않는다.

## 3-B. 의존성 정밀 검증 결과 (시행착오 차단 핵심)

> 결정: 분리 방식 = **탭 경계 정리(안 B)**, 착수 범위 = **진단서+예보 동시**.

### 이동 대상 = 진단서 "상세 섹션" 묶음의 전문 expander 6개

| # | expander | 라인 | 외부 의존 변수 | 상세탭 확보 | 안전등급 |
|---|----------|------|----------------|-------------|----------|
| 1 | 🔄 흐름과 연결 (🌊 2개 중첩 포함) | 23105 | chart, result | ✅✅ | 안전 |
| 2 | 💥 합국·방합 | 23218 | chart, result | ✅✅ | 안전 |
| 3 | ⚡ 충·형 신호 | 23224 | chart, result | ✅✅ | 안전 |
| 4 | ✨ 신살·특수신호 | 23230 | + payload, useful | ✅ payload=인자 / useful=result.get | 안전 |
| 5 | ⚖️ 신약신강 판단 | 23330 | + strength_index | ✅ 블록 내부서 result.get로 직접 추출 | 안전 |

**핵심 검증 사실:**
- 이동 블록들이 쓰는 지역변수(_active_flows, _flow_rows, _axis_results 등)는 **전부 블록 내부에서 자체 정의**된다. 함수 상위 스코프 의존 없음.
- 최종 외부 의존은 `chart`, `result`, `payload`, `useful` 4개뿐 → **전부 render_detail_tabs에 이미 존재** (chart/result/payload는 명시, useful은 result.get("useful")).
- `strength_index`는 지역변수가 아니라 ✨/⚖️ 블록 안에서 `result.get("strength_index", 50)`로 직접 추출 → result만 있으면 됨.
- 블록 내부 위젯 `key=` 사용 없음 → 상세탭 이동 시 key 중복 에러 불가능.

→ **변수 누락으로 인한 시행착오 가능성 = 0** (케미 빈화면 사고 유형 구조적으로 차단됨).

### 예보(render_sewun) 검토
- 🩺 세운 깊이 보기 = 전문체이나 **"올해" 맥락 전용** → 상세탭(원국 중심)으로 옮기면 맥락 단절. **예보에 유지 권장**.
- 결론: 예보는 expander 이동 없이, 톤 표준 주석만 부여.

### 톤 경계 정리 후 최종 구조
| 탭 | 내용 |
|----|------|
| 🏥 진단서 | 할머니 인트로 + 진단명 + 📋 처방전(생활처방) **만** — 순수 할머니체 |
| 🔎 상세 | 기존 + 이동된 전문 expander 6개 (흐름/합국/충형/신살/신약신강) |

## 3-C. 호출 그래프 · 격리 · 레이아웃 검증 (2차 정밀)

### ⚠️ 1차 설계의 치명적 오류 발견 → 수정
- **`render_detail_tabs`는 죽은 코드(dead code)였다.** 정의(25898)만 있고 호출처 0.
- 실제 🔎 상세보기 탭은 `render_single_summary`의 **인라인 분기(24353~)**가 직접 그림.
- → 1차 계획대로 render_detail_tabs로 옮겼다면 **화면에 안 나오는 헛수고**. 이 검증이 막아냄.
- **수정된 이동 목적지: `render_single_summary` 내 "🔎 전문가 상세보기" 인라인 분기 끝**
  (`render_shinsal_badge_cards(payload, prefix="single")` 호출 직후 위치에 append).

### 격리 검증 — 케미/맞짱/초대 영향 = 없음
진단서·상세 구성 함수 6개(render_hanuneyo, render_strength_operation_spotlight,
render_character_axis_cards, render_visual_analysis_core, render_shinsal_badge_cards)는
**전부 `render_single_summary`(혼자보기)에서만 호출.** 케미·맞짱·케미방은 0회 재사용.

| 화면 | 렌더 경로 | 진단서 함수 공유? |
|------|-----------|-------------------|
| 혼자보기(진단) | render_single_summary | (작업 대상) |
| 케미 | render_battle_result_board | ❌ 독립 |
| 모임케미 | render_multi_chem_result | ❌ 독립 |
| 맞짱방 | render_battle_room_page | ❌ 독립 |
| 케미방(초대) | render_chemistry_room_page | ❌ 독립 |

→ **톤 분리 작업이 케미/맞짱/초대로 번질 코드 경로가 물리적으로 없음.**

### 케미는 이미 모범 구현 (참고 모델)
케미는 "케미 한눈에(할머니체) ↔ 🔎 상세보기(expert_view 라디오: 관계분위기/상세케미/
합충형원진/대운세운/계산지표)"로 **우리가 진단서에 적용하려는 구조를 이미 완성**해 둠.
→ 진단서를 케미와 같은 모양으로 맞추면 앱 전체 일관성도 올라감.

### 레이아웃·색상 위험 = 없음
- 이동 대상 블록은 색을 **전부 인라인**(color:#..., background:#...)으로 지정.
- 외부 CSS `class=` 의존 **0개**.
- → 탭을 옮겨도 색/레이아웃 그대로 따라옴. 깨질 요소 없음.

## 4. 실행 계획 (단계별 — 각 단계 독립 배포 가능)

> 핵심: 한 번에 다 하지 않는다. 단계마다 push→확인→다음.

### 1단계: 경계 진단 (코드 변경 0)
- `render_hanuneyo_text_explanation`이 출력하는 모든 블록을 목록화
- 각 블록을 [할머니체 / 전문체 / 중립]으로 라벨링한 표 작성
- 산출물: "이동 대상 블록 목록" (어느 expander를 상세 탭으로 옮길지)

### 2단계: 전문 블록 이동
- 진단서의 전문 expander(처방전 상세·식상생재 흐름 등)를 상세 탭으로 이동
- 진단서에는 "자세한 근거는 🔎 상세 탭에서" 한 줄 안내만 남김
- 영향 범위: `render_hanuneyo` + `render_detail_tabs` 2개 함수만

### 3단계: 용어 칩 연결
- 할머니체 문장에 등장하는 GLOSSARY 용어를 자동 칩 처리
- 기존 `quest_title(terms=[...])` 인프라 재사용

### 4단계: 톤 표준 주석 삽입 + 잔여 정리
- 3-항의 톤 표준을 코드 주석으로 고정
- 남은 혼재 문장 일괄 점검

## 5. 리스크 및 시행착오 최소화 장치

| 리스크 | 대비책 |
|--------|--------|
| 블록 이동 중 변수 누락(케미 빈화면 사례 재발) | 이동 전 해당 블록이 쓰는 지역변수 의존성 먼저 grep |
| 톤 수정이 케미·뽑기 등 타 화면 오염 | 진단서/예보 함수에 국한, 공용 함수는 건드리지 않음 |
| 한 번에 너무 많이 → 디버깅 폭증 | 4단계 분할, 단계마다 문법검증+화면확인 |
| 할머니체 과다 제거로 "정 없는 앱" | 진단서는 톤 유지, 전문체는 상세 탭에만 |

## 6. 결정 필요 사항 (사용자 확인)

진행 전 아래를 정해야 한다:

1. **분리 강도**: 안 B(탭 경계 정리)로 갈지, 안 A(인라인 병기)도 섞을지
2. **전문 탭 깊이**: 상세 탭을 "전문가용"으로 더 무겁게 갈지, 적당히 유지할지
3. **용어 칩 범위**: 37개 용어 전부 칩 처리할지, 핵심 10개만 할지
4. **착수 범위**: 진단서만 먼저 할지, 예보까지 한 번에 할지

이 4가지가 정해지면 1단계(블록 라벨링)부터 무중단으로 진행 가능하다.
